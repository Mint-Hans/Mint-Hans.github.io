# 有趣的缓存

提到“缓存（Cache）”，写代码的同学第一反应通常是 CPU 的 L1/L2 Cache、Redis，或者是大模型推理里的 KV Cache。在这些场景里，缓存的唯一使命是**用空间换时间**——把算过的结果存下来，下次直接读，不做重复功。

但在游戏开发——尤其是动作游戏的角色控制器（Character Controller）里，“缓存”却扮演着另一个神奇的角色：**它不为了省算力，而是为了“修改规则”，给人类略显迟钝的神经反射提供时间上的温柔宽容。**

如果把缓存的定义放宽一点：**缓存，就是把过去产生、之后仍然有用的信息保存下来，让当前的行为能够利用它。** 顺着这个视角往下看，很多看似零散的机制突然就有了统一的脉络。

## 角色控制器里的“短期记忆”

在物理引擎眼里，世界是非黑即白的：这一帧脚下没有碰撞体，你就不能起跳；这一帧撞上了墙，你的水平速度就必须清零。但完全遵从物理真实的控制器，玩起来往往让人抓狂。

为了让操作“跟手”，我们需要在控制器里塞入不同类型的短期记忆。具体实现时，它们分别对应着**输入缓冲、状态资格、物理快照和历史序列**：

| 机制 | 保存或处理什么 | 作用 |
| --- | --- | --- |
| **输入缓冲** | 最近的输入及有效期 | 玩家稍早按下跳跃，落地后仍可执行 |
| **土狼时间** | 最近着地时间或起跳资格 | 刚离开平台边缘的极短时间内仍可起跳 |
| **平台动量暂存** | 最近的平台速度及有效期 | 平台刚停下瞬间起跳，仍可获得惯性助推 |
| **撞墙速度暂存** | 撞墙前的速度及有效期 | 短暂受阻后若及时脱离阻挡，可恢复原速度 |
| **连招历史** | 最近执行的动作序列 | 判断搓招组合，决定后续派生招式 |
| **KV Cache** | 历史 Token 在各层的 K 和 V | 复用中间计算结果，减少生成时的重复计算 |

看着这张表，你会发现《蔚蓝》（Celeste）这类顶级平台跳跃游戏的神级手感，很大程度上就是靠前四种“缓存”撑起来的：

* **输入缓冲（Input Buffer）缓存的是“未来的意图”**：玩家在落地前 3 帧按下了跳跃，此时角色还在空中，条件不满足。但别急着丢弃这个按键，把它存进有效期 0.1 秒的缓冲区里；等 3 帧后双脚沾地，立刻兑现起跳。
* **土狼时间（Coyote Time）缓存的是“过去的特权”**：玩家冲出悬崖边缘晚了 3 帧才按跳跃。虽然物理上已经悬空，但只要“最近着地计时器”还没归零，依然视为拥有起跳资格。
* **动量与速度暂存缓存的是“易逝的动能”**：高速移动的平台刚到终点停下，玩家晚了一拍起跳，如果直接按当前平台速度（0）计算，角色就会呆呆地原地跳起；把平台前几帧的速度暂存一下，就能打出漂亮的惯性超级跳。同理，高速冲刺时不小心蹭到墙角，暂存撞墙前的速度，只要玩家在几帧内滑开障碍，就能无损恢复冲刺。

## 别把所有“好手感”都算在缓存头上

聊到这里很容易产生一种错觉：是不是所有手感优化都是时间上的缓存？并不是。在角色控制器里，还有一些机制看起来很像缓存，但底层逻辑完全不同：

* **拐角修正（Corner Correction）**：角色起跳时脑袋蹭到上方台阶边缘，系统自动把角色往旁边挪几个像素让他顺利上去。这靠的是**碰撞检测与小幅位置调整**。
* **超级蹬墙跳的距离宽容**：哪怕角色还没有严丝合缝地贴住墙壁，隔着两三个像素按跳跃也能触发蹬墙跳。这靠的是**扩大空间检测范围（Raycast / Overlap）**。
* **速度分解**：斜着撞墙时不会原地卡死，而是顺着墙面滑行。这靠的是**运动学规则**——只抵消垂直于墙面的受阻速度分量，保留沿墙面切线方向的运动分量。
* **Q 弹的果冻感**：角色落地或撞墙停下时，身体会有一瞬间夸张的挤压、拉伸与恢复。此时物理碰撞体其实已经彻底停止了，动起来的是渲染层的 Sprite 形变，属于**视觉反馈与物理状态的解耦**。

**时间宽容（缓存）、空间宽容（检测放宽）、运动规则（速度分解）和视觉反馈（挤压拉伸）**，这四套工具各司其职。工程实现上，我们通常不需要去魔改底层物理引擎，只要在角色控制器层把它们组合起来，继续复用引擎原本的碰撞检测即可。

## 记住过去，会破坏状态机的马尔科夫性吗？

写状态机或做强化学习时，我们常听到一个词叫**马尔科夫性（Markov Property）**：系统的下一个状态只取决于当前状态，而与过去的历史无关。

既然缓存是“把过去的信息留到现在用”，这岂不是打破了马尔科夫性？

其实两者一点也不冲突。马尔科夫性真正关心的是：**当前状态所包含的信息，是否足以决定下一步的转移规律。** 当我们把“待执行的输入”、“暂存的速度向量”以及“剩余有效时间（TTL）”显式地作为字段塞进当前帧的 `State` 结构体后，过去的影响就已经被编码进了“现在”之中。状态机在推导下一帧时，只需要看当前帧的 `State` 即可，根本不需要再去翻阅完整的历史日志。

```cpp
// 把“过去”编码进当前状态，状态转移依然满足马尔科夫性
struct CharacterControllerState {
    Vec2  currentVelocity;
    bool  isGrounded;

    // 显式纳入当前状态的“短期记忆”
    float jumpBufferTimer = 0.0f;       // 输入缓冲剩余时间
    float coyoteTimer     = 0.0f;       // 土狼时间剩余时间
    Vec2  cachedPreWallVelocity;        // 撞墙前速度快照
    float wallVelRestoreTimer = 0.0f;   // 速度恢复有效窗口
};

```

## 同样是“记性好”，目的却截然不同

把游戏里的缓存和大模型的 **KV Cache** 放在一起对比，能看出一个很有意思的分界线：

* **改变规则的缓存**：输入缓冲、土狼时间、速度暂存，它们实实在在地**改变了系统的输出行为**。没有它们，这一帧你跳不起来；有了它们，你跳起来了。
* **纯粹提效的缓存**：标准的、无损的 KV Cache **绝对不会改变模型的输出结果**。无论开不开 KV Cache，Transformer 算出来的下一个 Token 分布是完全一致的，它只是把历史 Token 在每一层算好的 Key 和 Value 矩阵存下来，避免自回归生成时每次都从头重算一遍。
* **回溯与叙事型记忆**：除了控制和算力，游戏里还会用历史记录做很多酷炫的设计。比如把过去十几帧的坐标和姿态存进环形缓冲区（Ring Buffer），就能渲染出冲刺时的**残影**；潜行游戏里敌人丢失视野后，会走向玩家的**最后目击位置（Last Known Position）**；而如果把状态快照扩展到全局，就能做出《时空幻境》（Braid）里的**时间倒带**——当然，做完整倒带时就得仔细权衡：到底哪些世界状态需要恢复，哪些可以忽略。

## 落地实战：设计检查表与“引用陷阱”

下次在给游戏写控制器或者设计任何带“记忆”的机制时，可以直接套用这四个灵魂拷问：

1. **记什么**：存的是按键输入、速度向量、离散状态，还是纯粹的计算结果？
2. **何时记**：是在每帧 `Update` 时刷新、特定碰撞事件触发时记录，还是状态机切换的瞬间定格？
3. **何时用**：满足什么前置条件时，才把这份记忆拿出来读取或执行？
4. **何时失效**：是倒计时结束自动过期、被消费一次后立刻清零（比如土狼时间起跳后必须立刻失效，否则会变成无限连跳）、还是环境改变/状态切换时强制作废？

最后，还要警惕一个代码实现中极易踩中的坑：**保存了对象的引用或指针，不等于保存了过去。**

```cpp
// 错误示范：存了引用/指针，历史快照会跟着当前对象一起被修改！
Transform* lastKnownTransform = player->getTransform(); 

// 正确示范：值拷贝你需要的那部分历史快照
Vec3 lastKnownPosition = player->getTransform()->position;

```

当你需要的是一份“历史快照”时，务必老老实实复制（深拷贝或值拷贝）当时的数据。如果图省事存了一个可变对象的引用，等到下一帧原对象的速度或位置被物理引擎改写，你缓存里的“过去”也就跟着被篡改了。

从几毫秒的按键宽容，到大模型显存里吞吐的张量，缓存看似只是一个工程小技巧，背后藏着的却是我们处理“时间”与“状态”的哲学。
