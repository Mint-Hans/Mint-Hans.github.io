# 有趣的缓存

提到“缓存（Cache）”，写代码的同学第一反应通常是 CPU 的 L1/L2 Cache、Redis，或者是大模型推理里的 KV Cache。在这些经典场景里，缓存的核心使命是用空间换时间——把算过的结果存下来，下次直接读取，绝不做重复功。

但在游戏开发——尤其是动作游戏的角色控制器（Character Controller）里，“缓存”却扮演着另一个截然不同的角色：**它不为了省算力，而是为了“修改规则”，给人类略显迟钝的神经反射提供时间上的温柔宽容。**

如果把缓存的定义放宽一点：**缓存，就是把过去产生、之后仍然有用的信息保存下来，让当前的行为能够利用它。** 顺着这个视角往下看，很多看似零散的游戏机制突然就有了统一的脉络。

---

## 角色控制器里的“短期记忆”

在物理引擎眼里，世界是非黑即白的：这一帧脚下没有碰撞体，你就不能起跳；这一帧撞上了墙，你的水平速度就必须清零。但完全遵从物理真实的控制器，玩起来往往让人抓狂。

为了让操作“跟手”，我们需要在控制器里塞入不同类型的短期记忆。具体到工程实现上，它们分别对应着输入缓冲、状态资格、物理快照和历史序列：

| 机制 | 保存或处理什么 | 作用 |
| --- | --- | --- |
| **输入缓冲** | 最近的输入及有效期 | 玩家稍早按下跳跃，落地后仍可执行 |
| **土狼时间** | 最近着地时间或起跳资格 | 刚离开平台边缘的极短时间内仍可起跳 |
| **平台动量暂存** | 最近的平台速度及有效期 | 平台刚停下瞬间起跳，仍可获得惯性助推 |
| **撞墙速度暂存** | 撞墙前的速度及有效期 | 短暂受阻后若及时脱离阻挡，可恢复原速度 |
| **连招历史** | 最近执行的动作序列 | 判断搓招组合，决定后续派生招式 |
| **KV Cache** | 历史 Token 在各层的 K 和 V | 复用中间计算结果，减少生成时的重复计算 |

看着这张表，你会发现《蔚蓝》（Celeste）这类顶级平台跳跃游戏的神级手感，很大程度上就是靠前几种“缓存”撑起来的：

* **输入缓冲（Input Buffer）缓存的是“未来的意图”**：玩家在落地前 3 帧按下了跳跃，此时角色还在空中，起跳条件不满足。控制器不会直接丢弃这个按键，而是把它存进有效期 0.1 秒的缓冲区里；等 3 帧后双脚沾地，立刻兑现这次起跳。
* **土狼时间（Coyote Time）缓存的是“过去的特权”**：玩家冲出悬崖边缘晚了 3 帧才按跳跃。虽然物理上已经悬空，但只要“最近着地计时器”还没归零，系统依然视其拥有地面起跳资格。
* **动量与速度暂存缓存的是“易逝的动能”**：高速移动的平台刚到终点停下，玩家晚了一拍起跳，如果直接按当前平台速度（0）计算，角色就会呆呆地原地跳起；把平台前几帧的速度暂存一下，就能打出漂亮的惯性超级跳。同理，高速冲刺时不小心蹭到墙角，暂存撞墙前的速度，只要玩家在几帧内滑开障碍，就能无损恢复冲刺。

## 别把所有“好手感”都算在缓存头上

聊到这里很容易产生一种错觉：是不是所有手感优化都是时间上的缓存？并不是。在角色控制器里，还有一些高频机制看起来很像缓存，但底层完全不依赖历史记忆，而是**空间几何**与**表现层**的技巧：

* **拐角修正（Corner Correction）——基于多射线探测的瞬时位移补偿**
角色跳跃上升时，如果头顶边缘擦到上方台阶的角，按纯物理碰撞会被直接顶停、垂直速度清零。工程上的做法是在角色头顶左右两侧布置一组向上的探测射线（或做极小步长的 Sweep Test）：当**外侧射线命中台阶、内侧射线未命中**，且遮挡深度小于设定的宽容阈值（例如 4~6 像素）时，控制器会在**当前帧**直接对角色施加一个水平方向的瞬时位置偏移（`position.x += nudgeOffset`），把角色“挤”出障碍边缘，同时完整保留向上的跳跃速度。整个过程只看当前帧的空间几何关系，不需要记住任何过去的状态。
* **超级蹬墙跳的距离宽容——物理碰撞体与判定框的解耦**
这里需要做一个精细区分：“离开墙面后几帧内仍可蹬墙跳”确实是时间缓存（Wall Coyote Time）；但“角色还没严丝合缝地贴住墙壁、隔着两三个像素按跳跃就能蹬墙”靠的则是**空间探测外扩**。工程上我们不会去把物理碰撞体改大（那会导致角色视觉穿模或卡进墙里），而是从碰撞体左右两侧额外发射略长于皮肤厚度（Skin Width）的水平射线（Raycast / BoxCast）。即便物理引擎判定 `isTouchingWall == false`，只要逻辑探测射线在当前帧命中了墙体，就直接赋予蹬墙跳资格——这是纯空间维度的宽容，无状态、无记忆。
* **速度分解（Velocity Decomposition）——基于法线投影的运动学约束**
玩家斜着冲向墙壁或斜坡时，不会像粘在胶水上一样原地卡死，而是顺着表面平滑滑行。这靠的不是记录历史速度，而是**向量正交分解**。当角色以速度向量 $\vec{v}$ 撞击法线为单位向量 $\vec{n}$ 的接触面时，暴力清零会让所有动能瞬间丢失；正确的做法是通过点积求出垂直于表面的受阻分量 $(\vec{v} \cdot \vec{n})\vec{n}$ 并将其剔除，仅保留沿切线方向的分量：

$$\vec{v}_{\text{slide}} = \vec{v} - (\vec{v} \cdot \vec{n})\vec{n}$$



现代运动学控制器（如经典的 `CollideAndSlide` 迭代算法）在单帧内就能完成碰撞检测、位置回退与速度投影，完全属于当前帧的几何求解。
* **Q 弹的果冻感（Squash & Stretch）——逻辑状态与视觉表现的解耦**
角色高速落地或撞墙停下时，身体会有一瞬间夸张的压缩、拉伸与回弹。实际上，物理碰撞体（Collider）在接触瞬间就已经彻底静止，坐标不再变化；真正动起来的是挂载在子节点上的渲染图层或网格缩放矩阵（Scale）。这是用动画曲线欺骗眼睛的视觉反馈，与物理计算彻底分离。

**时间宽容（缓存）、空间宽容（探测外扩与位置补偿）、运动规则（向量投影）和视觉反馈（形变动画）**，这四套工具各司其职。工程实现上，我们通常不需要魔改底层物理引擎，只需在角色控制器这一层将它们正交组合，继续复用引擎底层的碰撞查询即可。

## 记住过去，会破坏状态机的马尔科夫性吗？

写状态机或接触强化学习时，我们常听到一个概念叫**马尔科夫性（Markov Property）**：系统的下一个状态只取决于当前状态，而与过去的历史无关。

既然缓存是“把过去的信息留到现在用”，这岂不是打破了马尔科夫性？

其实两者并不冲突。马尔科夫性真正关心的是：**当前状态所包含的信息，是否足以决定下一步的转移规律。** 在控制论里，这叫“状态空间增广（State Augmentation）”——只要我们把“待执行的输入”、“暂存的速度向量”以及“剩余有效时间（TTL）”显式地作为字段塞进当前帧的 `State` 结构体里，过去的影响就已经被编码进了“现在”之中。状态机在推导下一帧时，只需要读取当前帧的 `State`，根本不需要再去翻阅完整的历史日志。

```cpp
// 把“过去”显式编码进当前状态，状态转移依然满足马尔科夫性
struct CharacterControllerState {
    Vec2  currentVelocity;
    bool  isGrounded;

    // 纳入当前状态向量的“短期记忆”
    float jumpBufferTimer     = 0.0f;   // 输入缓冲剩余时间
    float coyoteTimer         = 0.0f;   // 土狼时间剩余时间
    Vec2  cachedPreWallVelocity;        // 撞墙前速度快照
    float wallVelRestoreTimer = 0.0f;   // 速度恢复有效窗口
};

```

## 同样是“记性好”，目的却截然不同

把游戏里的缓存和大模型的 KV Cache 放在一起对比，能看出一条很有意思的分界线：

* **改变规则的缓存**：输入缓冲、土狼时间、速度暂存，它们实实在在地改变了系统的输出行为。没有它们，这一帧你跳不起来；有了它们，你跳起来了。
* **纯粹提效的缓存**：标准的、无损的 KV Cache 不会改变模型的输出结果。无论开不开 KV Cache，Transformer 算出来的下一个 Token 概率分布是完全一致的，它只是把历史 Token 在每一层算好的 Key 和 Value 矩阵存下来，避免自回归生成时每次都从头重算一遍（当然，工程上若引入 KV 量化或窗口淘汰，才会变成一种有损近似）。
* **回溯与叙事型记忆**：除了操控手感和算力优化，游戏里还会用历史记录做很多玩法设计。比如把过去十几帧的坐标和姿态存进环形缓冲区（Ring Buffer），就能渲染出冲刺时的残影；潜行游戏里敌人丢失视野后，会走向玩家的最后目击位置（Last Known Position）；而如果把状态快照扩展到全局，就能做出《时空幻境》（Braid）里的时间倒带——当然，做完整倒带时就得仔细权衡：到底哪些世界状态需要入栈恢复，哪些粒子特效或音效可以忽略。

## 落地实战：设计检查表与“引用陷阱”

下次在给游戏写控制器，或者设计任何带“记忆”的机制时，可以直接套用这四个检查项：

1. **记什么**：存的是离散按键输入、连续速度向量、状态标记，还是纯粹的中间计算结果？
2. **何时记**：是在每帧 `Update` 时持续刷新、特定碰撞事件触发时记录，还是状态机切换的瞬间定格？
3. **何时用**：满足什么前置条件时，才把这份记忆拿出来读取或执行？
4. **何时失效**：是倒计时结束自动过期、状态切换时强制作废，还是**被消费一次后立刻清零**？（比如利用土狼时间起跳的瞬间，必须同时把 `coyoteTimer` 和 `jumpBufferTimer` 归零，否则状态切换稍有延迟就会引发无限连跳或双重触发 Bug。）

最后，还要警惕一个代码实现中极易踩中的坑：**保存了对象的引用或指针，不等于保存了过去。**

```cpp
// 错误示范：存了指针/引用，历史快照会跟着当前对象一起被物理引擎改写！
Transform* lastKnownTransform = player->getTransform(); 

// 正确示范：值拷贝你需要的那部分历史快照
Vec3 lastKnownPosition = player->getTransform()->position;

```

当你需要的是一份“历史快照”时，务必老老实实复制（值拷贝或深拷贝）当时的数据。如果图省事存了一个可变对象的引用，等到下一帧原对象的坐标或速度被物理引擎修改，你缓存里的“过去”也就跟着被篡改了。

从几毫秒的按键宽容，到大模型显存里吞吐的张量，缓存看似只是一个工程技巧，背后藏着的却是我们处理“时间”与“状态”的哲学。
